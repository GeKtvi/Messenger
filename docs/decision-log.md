# Decision log

Architecture, tooling and convention decisions for Pingo, newest last.

**Rules**

- Add an entry in the same commit as the change that implements the decision.
- Never rewrite the decision of an accepted entry. To change course, add a new entry
  and set the old one's status to `Superseded by D-NNN`.
- Keep entries short: what was decided, why, and what it costs.

**Entry template**

```markdown
## D-NNN: <short title>

- **Date:** YYYY-MM-DD
- **Stage:** NN
- **Status:** Accepted | Superseded by D-NNN

**Context:** what problem or question came up.

**Decision:** what we chose.

**Consequences:** trade-offs, follow-ups, what this rules out.
```

## D-001: Build the project in C# on .NET 10

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The homework requires a `.sln`, EF Core, Blazor WebAssembly and MudBlazor.

**Decision:** Use C# on .NET 10 (the installed SDK, 10.0.401) for both backend and frontend.

**Consequences:** The whole stack is one language and one toolchain.

## D-002: Solution layout: one folder per microservice

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The task asks for `Services/<ServiceName>` and a `Frontend` folder next to it.

**Decision:** Each microservice keeps all its projects in its own folder under `Services/`
(for example `Services/Message/`). The UI lives under `Frontend/`. The `.sln` mirrors this with
solution folders.

**Consequences:** New services get a new folder. Shared code, if any, will need its own place later.

## D-003: Store messages in SQLite for the first stage

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Superseded by D-008

**Context:** Stage 01 only said "store data with EF Core".

**Decision:** Use the SQLite EF Core provider with a local `messages.db` file.

**Consequences:** Zero setup, but no real database server. SQLite can't sort by `DateTimeOffset`
in SQL, so messages were sorted in memory.

## D-004: Create the schema with `EnsureCreated`, not migrations (for now)

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Superseded by D-021

**Context:** The model is tiny and changing quickly.

**Decision:** Call `Database.EnsureCreated()` on startup instead of using EF Core migrations.

**Consequences:** `EnsureCreated` cannot change an existing schema. Any model change (for example
adding an edit time) needs either a dropped database or a switch to migrations. Revisit when the
model changes.

## D-005: Use `Guid` message ids

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** Messages need an id. Later the client will choose ids for idempotent `PUT` requests.

**Decision:** Use `Guid` ids from the start.

**Consequences:** Ids can be generated by the client without coordinating with the database.
Stage 02's "change id from `int` to `Guid`" is already satisfied.

## D-006: Frontend: typed API client, API address in config

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The Blazor app is served from a different origin than the API.

**Decision:** Wrap API calls in a `MessageApiClient` class. Read the API base URL from
`wwwroot/appsettings.json`. The API allows the frontend origins through a CORS policy configured in
its `appsettings.json`.

**Consequences:** Pages don't build URLs themselves. Changing ports or hosts is a config change.

## D-007: Mark stages with two-digit annotated git tags

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** Reviewers need a stable pointer to each finished homework stage.

**Decision:** Tag each finished stage with an annotated tag `01`, `02`, ... The stage table in
`README.md` is updated in the tagged commit. Tags are never moved; fixes go into the next stage.

**Consequences:** The stage 01 tag was moved once, at the owner's request, when its two commits
were squashed before review. That was a one-off exception, not a change to the rule.

## D-008: Move message storage to PostgreSQL in Docker

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 requires PostgreSQL.

**Decision:** Use the Npgsql EF Core provider. Run PostgreSQL 17 locally with `docker-compose.yml`.
Put the dev connection string only in `appsettings.Development.json`.

**Consequences:** Local runs need Docker. Sorting now happens in SQL. Existing SQLite test data was
not migrated (big-bang switch to an empty database), which was acceptable because it was test data
only.

## D-009: Use `TypedResults` with explicit result types

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Endpoints returned `IResult`, which hides the possible responses.

**Decision:** Return `TypedResults` with typed signatures (for example `Task<Ok<List<...>>>`,
`Task<Created<...>>`).

**Consequences:** The compiler checks the result types, and OpenAPI picks up response codes
automatically. Responses produced outside the action (such as automatic 400s) need
`[ProducesResponseType]`.

## D-010: `GetAll` returns every message (scaffold only)

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The homework only asks to "show all messages".

**Decision:** Load and return every message with no paging. Mark it with a "Scaffold only"
comment in `MessageService.GetAllAsync`.

**Consequences:** Fine for a demo, unusable at scale. Replace with cursor-based paging (for example
`?before=<sentAt>&limit=50`) before real use.

## D-011: Use MVC controllers for the API layer

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 01 used minimal API endpoints. Stage 02 talks about controllers.

**Decision:** Replace `MessageEndpoints` with `MessagesController` (`[ApiController]`).

**Consequences:** Matches the homework wording and reviewer expectations. Slightly more ceremony
than minimal APIs.

## D-012: Split into an API layer and a `Pingo.Messages` business layer

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 requires controllers that only accept requests and call a business layer,
without knowing what's inside it.

**Decision:** Add `Services/Message/Pingo.Messages` (class library). It owns the `DbContext`,
entities, EF Core/Npgsql packages and `MessageService`. Only `IMessageService`, `Models.*`,
`MessageLimits` and the `AddMessages(...)` DI extension are public. Everything else is `internal`.

**Consequences:** The compiler enforces the boundary: the API project cannot reach the database.
Tests that need internals will need `InternalsVisibleTo`.

## D-013: Separate database entities from business models

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The business layer needs something to return to the controller.

**Decision:** Keep `Entities.Message` (internal, mutable, shaped by the database) separate from
`Models.Message` (public immutable record, shaped by callers). Map between them in `MessageService`.
Where both are used, alias the entity as `MessageEntity`.

**Consequences:** Database changes don't leak into the API, and callers never get EF-tracked
objects. Costs a second, near-identical class and a one-line mapping.

## D-014: Validate requests with DataAnnotations, guard again in the service

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Validation was hand-written inside the endpoint.

**Decision:** Put `[Required]` and `[MaxLength(MessageLimits.MaxTextLength)]` on
`SendMessageRequest` and let `[ApiController]` return 400 automatically. `MessageService` also
checks its inputs and trims the text, so it doesn't rely on the caller.

**Consequences:** Controllers stay thin. The 2000-character limit lives in one constant shared by the
API contract and the database mapping.

## D-015: Get the current time from `TimeProvider`

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Send and edit times will be asserted in component tests.

**Decision:** Inject `TimeProvider` into `MessageService` (registered with `TryAddSingleton`)
instead of calling `DateTimeOffset.UtcNow`.

**Consequences:** Tests can swap in a fake clock.

## D-016: Name everything "Pingo"

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The homework calls the business layer `Pingo.Messages`, while the rest used
`Messenger.*`.

**Decision:** Rename the solution and projects to `Pingo.sln`, `Pingo.Messages.Api`,
`Pingo.Messages` and `Pingo.Frontend`, with matching namespaces and "Pingo" as the UI title.

**Consequences:** Kept unchanged on purpose: the GitHub repo name (`Messenger`), the local folder,
and the local PostgreSQL names (`messenger-postgres`, `messenger_messages`), because renaming them
would recreate the database.

## D-017: Use `init` for entity properties that never change

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Entity properties were all `get; set;`.

**Decision:** Make `Id` and `SentAt` `init`. Keep `Text` settable because idempotent `PUT` will
edit it.

**Consequences:** The compiler blocks accidental changes to identity and send time. EF Core still
materializes the entity through its backing fields.

## D-018: No route names on controller actions

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Route names (`[HttpGet(Name = "GetMessages")]`) were carried over from the minimal API
version. Nothing used them for link generation.

**Decision:** Drop them.

**Consequences:** OpenAPI operations have no `operationId`, so generated clients would invent
method names. Add `[EndpointName(...)]` if a client is ever generated.

## D-019: Use the `.slnx` solution format and list docs in the solution

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The solution was a classic `.sln` file: verbose, full of GUIDs, and hard to review in
diffs. Markdown docs weren't visible in the IDE's Solution Explorer.

**Decision:** Migrate `Pingo.sln` to `Pingo.slnx` (the XML solution format supported by .NET 9+
and Visual Studio 2022 17.13+), drop the unused x64/x86 platforms, and add the Markdown files as
solution items: `README.md` and `CLAUDE.md` under "Solution Items", the decision log under "docs".

**Consequences:** The solution file is short and readable in diffs. Older tooling that only
understands `.sln` can't open it. New Markdown docs must be added to `Pingo.slnx` by hand to show up
in the IDE.

## D-020: Send request is a class with properties

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 asks that the send action accept a dedicated class with a text property, not a
string or the message model, so more parameters can be added later. `SendMessageRequest` was a
positional record, so each new field would have become another constructor parameter.

**Decision:** Make `SendMessageRequest` a class with an `init` `Text` property (defaulting to an empty
string) and keep the validation attributes on the property.

**Consequences:** New optional fields are just new properties, and existing clients keep working.
Missing, null and blank text all produce the same "Message text is required." error. Unknown JSON
fields are ignored.

## D-021: Manage the schema with EF Core migrations

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Adding the edit time is the first model change. `EnsureCreated` (D-004) cannot add a
column to an existing table, and dropping the database would lose its messages.

**Decision:** Use EF Core migrations, stored in `Services/Message/Pingo.Messages/Data/Migrations`.
The API applies pending migrations on startup (`MigrateMessagesDatabaseAsync`). Non-relational
providers, such as the in-memory database for tests, fall back to `EnsureCreated`. `dotnet-ef` is a
local tool pinned in `dotnet-tools.json`, and `Microsoft.EntityFrameworkCore.Design` is a build-only
reference in the API project.

The existing database was baselined: the `InitialCreate` migration was checked against the live
table and recorded in `__EFMigrationsHistory` by hand, so only `AddMessageUpdatedAt` ran against it.

**Consequences:** Every model change now needs a migration
(`dotnet ef migrations add <Name> --project Services/Message/Pingo.Messages --startup-project
Services/Message/Pingo.Messages.Api --output-dir Data/Migrations`). Migrating on startup is fine for
one instance; with several instances, migrations should run as a separate deployment step.

## D-022: Track the edit time as a nullable `UpdatedAt`

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 asks to store both the send time and the last edit time, with null when the
message was never edited.

**Decision:** Add `DateTimeOffset? UpdatedAt` to the entity, business model, API response and
frontend DTO, next to the existing `SentAt`. It stays null until an edit sets it (step 5). The UI
shows "· edited", with the edit time on hover, when it's set.

**Consequences:** Clients can tell edited messages apart without a separate flag. `SentAt` remains
the sort key, so edits don't reorder the chat.

## D-023: Send with idempotent `PUT /api/messages/{messageId}`

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 replaces `POST /api/messages` with `PUT /api/messages/{messageId}`: create the
message the first time, otherwise update its text and edit time.

**Decision:**

- The client generates the message id. `POST` is removed.
- `MessageService.SendAsync(id, text)` creates or updates and returns `SendMessageResult(Message,
  Created)`. The controller maps that to `201 Created` or `200 OK`.
- Only a *different* text counts as an edit. Repeating an identical request changes nothing, not even
  `updatedAt`, so the operation is truly idempotent and retries are safe.
- If two requests insert the same new id at the same moment, the loser catches the PostgreSQL unique
  violation (`23505`) and continues as an update instead of returning a 500.
- The frontend keeps the id of a failed send and reuses it on retry, so a lost response can't create
  a duplicate.
- `Guid.Empty` is rejected with 400. A non-Guid id doesn't match the route (404).

**Consequences:** Clients can retry freely. Anyone who knows a message id can edit it, which is
accepted while the chat is anonymous; ownership checks come with users. The duplicate-insert
fallback relies on PostgreSQL error codes and hasn't been exercised yet: ten concurrent requests in
manual testing didn't overlap, and the in-memory test database can't reproduce it.

## D-024: Development-only delay for message sends

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Superseded by D-026

**Context:** Sends are fast locally, so the UI's sending state, retries and concurrent sends can't be
observed by hand.

**Decision:** Add a small middleware in the API's `Program.cs` that delays every `PUT` by
`Testing:SendDelayMs` milliseconds. It only runs in the Development environment, is `0` (off) in
`appsettings.Development.json`, and logs a warning at startup when enabled. Turn it on per run with
the `Testing__SendDelayMs` environment variable.

**Consequences:** It can't affect Production, and it keeps test-only code out of the controller and
the business layer. Because it delays the request before the controller, concurrent requests are
slowed but not synchronized, so it doesn't reproduce the duplicate-insert race from D-023. A test
for that would need a pause between the lookup and the insert inside `MessageService`.

## D-025: Optimistic sending with a persistent outbox in the frontend

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The UI locked the input while a message was being sent, and a failed send was only a
popup. With a slow server, the chat felt frozen, and a reload lost anything unsent.

**Decision:** Add a `MessageOutbox` service in the frontend, like a messenger's outbox:

- A new message gets its id on the client and appears immediately as "Sending…". The input stays
  usable, so several messages can be pending at once.
- On success it's replaced by the server's copy. On failure it's shown as "Not sent" with Retry
  (same id) and Discard.
- Pending messages are saved in `localStorage` under `pingo.outbox` and resent automatically when
  the app starts.

**Consequences:** Retries and resends after a reload are safe only because `PUT` is idempotent
(D-023). The outbox lives in one browser, so it doesn't follow the user to another device. There's
no automatic retry with backoff yet: a failed message waits for Retry or the next page load. A
message rejected by validation (400) also shows as "Not sent", and retrying it won't help.

## D-026: Remove the development send delay

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The send delay from D-024 was added to try out the UI's sending state, retries and the
outbox (D-025) by hand. That testing is done.

**Decision:** Remove the middleware, the `Testing:SendDelayMs` setting and its README section.

**Consequences:** The API has no test-only code paths. To slow sends down again, use the browser's
network throttling, or restore the middleware from git history (commit with D-024).

## D-027: Component tests with `WebApplicationFactory` and an in-memory database

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 asks for component tests in a new `Pingo.Messages.ComponentTests` project using
xUnit, `Microsoft.AspNetCore.Mvc.Testing` and FluentAssertions. The service starts once through an
`IClassFixture`, the database is replaced with an in-memory one, and it's emptied before each test.

**Decision:**

- `MessagesApiFactory : WebApplicationFactory<Program>` is the class fixture. It runs the app in the
  `Testing` environment, swaps PostgreSQL for the EF Core in-memory provider (removing both
  `DbContextOptions<MessageDbContext>` and EF Core 9+'s `IDbContextOptionsConfiguration`), and
  replaces `TimeProvider` with a `FakeTimeProvider`.
- Each test class gets its own in-memory database name. Each test empties the database through
  `IAsyncLifetime.InitializeAsync` (`EnsureDeleted` + `EnsureCreated`).
- The API's `Program` is exposed with `public partial class Program;`. `Pingo.Messages` grants
  `InternalsVisibleTo` only to the test project, so it can reach `MessageDbContext`.
- FluentAssertions is pinned to 7.x: 8.x moved to a paid licence for commercial use, while 7.x is
  Apache 2.0.
- Tests cover the four required scenarios plus an identical repeat (no edit) and blank text (400).

**Consequences:** The tests need no Docker and run in under a second. Deliberately breaking the
ordering and the idempotency logic made the matching tests fail. The in-memory provider isn't a real
database: it doesn't enforce SQL constraints or raise PostgreSQL errors, so the duplicate-insert
fallback (D-023) and migrations are still untested. Testcontainers with a real PostgreSQL would
cover those.

## D-028: Concurrency tests on real PostgreSQL with a forced race

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** D-023's fallback for two requests creating the same id at once had never run: manual
tests never produced an overlap, and the in-memory test database (D-027) can't raise PostgreSQL's
duplicate-key error.

**Decision:**

- Add `MessagesConcurrencyTests`, which run the service against a real PostgreSQL 17 started with
  Testcontainers (`PostgresMessagesApiFactory`). The app applies its migrations on startup, so
  migrations are tested too.
- Force the race with an EF Core `SaveChangesInterceptor` in the test project (`InsertGate`): it
  holds every insert until all expected requests have reached it, then releases them together.
  No test code goes into the app.
- Tag the class `[Trait("Category", "Docker")]` so it can be skipped with
  `--filter "Category!=Docker"`.
- Add `MessagesIdempotencyTests` (in-memory) for repeated requests, repeated edits, whitespace-only
  differences and stale retries. Both factories share `MessagesApiFactoryBase`.

**Consequences:** The full test run needs Docker and takes a few seconds longer. The fallback now
runs on every test run (13 duplicate-key rejections handled per run), and breaking it fails two
tests. The stale-retry test records a known limit: an old request arriving after a newer edit
reverts the text, because plain `PUT` has no version check (ETag / `If-Match`).

## D-029: Round send and edit times to microseconds

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** .NET times have 100 ns ticks, but PostgreSQL `timestamptz` keeps microseconds. The
response to a create was built from the in-memory entity, so its `sentAt` could differ slightly from
what every later read returned, breaking D-023's "a retry returns the same data". Tests missed it
because the fake clock started on a whole second.

**Decision:** `MessageService` rounds `SentAt` and `UpdatedAt` down to the microsecond before
storing them. `MessagesPostgresStorageTests` checks it with a clock that has sub-microsecond ticks.

**Consequences:** Responses and reads always agree. Times are microsecond-precise, which is far
finer than a chat needs.

## D-030: The text length limit counts the trimmed text

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** `[MaxLength]` checked the raw request text, but the service trims it before storing. So
2000 characters with surrounding spaces were rejected even though the stored text would fit.

**Decision:** Validate with `TrimmedMaxLengthAttribute`, which derives from `MaxLengthAttribute`
and trims before checking. The limit applies to the text that is actually stored.

**Consequences:** Deriving from `MaxLengthAttribute` keeps `maxLength` in the OpenAPI schema. The
schema slightly understates what is accepted: a longer body passes if the extra is only surrounding
whitespace.

## D-031: Order messages with the same send time by id

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Messages are listed by `SentAt` (D-022). Two messages with the same time had no defined
order, so PostgreSQL could return them differently on each read.

**Decision:** Order by `SentAt`, then by `Id`.

**Consequences:** The list order is stable. Ids are random Guids, so ties are ordered arbitrarily but
consistently. PostgreSQL and .NET compare Guids differently, so the frontend's local sort may order
an exact tie differently until the next reload.

## D-032: Identity service with an API project and a business project

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03 adds an authentication service (registration, login, tokens) with a Web API
project and a business-logic project, in its own `Identity` folder.

**Decision:** Add `Services/Identity/Pingo.Identity.Api` (controllers, HTTP) and
`Services/Identity/Pingo.Identity` (business layer, storage, tokens), following D-002 and D-012.
The API registers the business layer with `AddPingoIdentity()`; the name avoids clashing with

**Consequences:** The two services share no code. Anything common (for example JWT settings that
the Message service will need to validate tokens) will need a decision on where it lives.

## D-033: Swagger UI on top of the built-in OpenAPI document

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03 is tested by hand through Swagger. The APIs already generate their OpenAPI
document with `Microsoft.AspNetCore.OpenApi`, which has no UI.

**Decision:** Add only `Swashbuckle.AspNetCore.SwaggerUI` and point it at `/openapi/v1.json`, in

**Consequences:** One package, no second document generator. The Message API doesn't have the UI

## D-034: Identity storage: Dapper on PostgreSQL with hand-written SQL migrations

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03 forbids EF Core in the Identity service: queries are written by hand with
Dapper, and migrations are SQL constants in raw string literals in the code.

**Decision:**

- `Pingo.Identity` uses Dapper over Npgsql, with one `NpgsqlDataSource` (connection pool) owned by
  the internal `IdentityDatabase` singleton.
- Migrations live in `Data/Migrations.cs` as `Migration(Version, Name, Sql)` records. Applied
  versions are recorded in a `schema_migrations` table.
- Each migration runs in its own transaction together with its history row, so a failure leaves
  nothing half-applied. PostgreSQL supports transactional DDL, so this covers schema changes too.
- A PostgreSQL advisory lock around the whole run lets only one instance migrate at a time.
- An applied migration is never edited; mistakes are fixed by a new migration.
- Tables and columns use `snake_case`, the PostgreSQL convention.

**Consequences:** No down migrations: rolling back means writing a new forward migration. A
migration that can't run in a transaction (for example `CREATE INDEX CONCURRENTLY`) would need a
flag to opt out.

## D-035: Apply Identity migrations in a `BackgroundService`, holding queries until done

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03 asks for migrations to be applied in a `BackgroundService`. A background
service runs alongside startup, so the API can accept requests before the schema exists.

**Decision:** `DatabaseMigrator : BackgroundService` creates the database if needed and applies the
migrations. `IdentityDatabase.OpenConnectionAsync` waits until the migrator reports success, so a
request that arrives early waits for the schema instead of failing. If migrating fails, the
exception stops the host (the default `BackgroundServiceExceptionBehavior.StopHost`), and
waiting requests get the same error.

**Consequences:** Startup is not delayed by migrations, and no query can run against a half-built
schema. With several instances, migrating on startup works thanks to the advisory lock (D-034), but
a separate deployment step would be the usual choice in production.

## D-036: Separate `pingo_identity` database, created by the service on first start

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Each microservice should own its data. The local PostgreSQL container
(`docker-compose.yml`) only creates the Message service's database, and its init scripts would
not run on an existing volume.

**Decision:** The Identity service uses its own database, `pingo_identity`, in the same local
PostgreSQL container. The migrator connects to the `postgres` maintenance database and creates
`pingo_identity` if it doesn't exist.

**Consequences:** No manual setup is needed locally. Creating the database requires the
`CREATEDB` permission, which the local development user has. In production the database would be
provisioned in advance and this step would find it already there.

## D-037: Users and password sign-ins in separate tables

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03 requires the login details to live apart from the user, because other ways
to sign in (for example OAuth) may come later.

**Decision:** `users` holds only `id` and `registered_at`. `password_logins` holds `user_id`
(primary key, a foreign key to `users`, deleted with the user), `email` (unique), `password_hash`,
`password_salt`, `password_iterations` and `created_at`. Registration inserts both rows in one
transaction. New user ids are `Guid.CreateVersion7()`, which are time-ordered and keep the primary
key index compact.

**Consequences:** A future `oauth_logins` table can point at the same `users` row. With one row
per user in `password_logins`, a user has at most one email and password.

## D-038: Hash passwords with PBKDF2-HMAC-SHA256 and a per-password salt

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** Passwords must be stored hashed with a salt. A plain hash such as SHA-256 is far too
fast: a GPU can try billions of guesses a second against a leaked table.

**Decision:** Use `Rfc2898DeriveBytes.Pbkdf2` (built into .NET) with SHA-256, 600 000 iterations
(OWASP's current recommendation), a random 16-byte salt per password and a 32-byte hash. The
iteration count is stored with each hash so it can be raised later. Verification compares hashes
with `CryptographicOperations.FixedTimeEquals`.

**Consequences:** No extra package. Each hash takes about 80 ms of CPU, which slows attackers down,
but also means many registration or login requests at once can load the server, so rate limiting
will matter later. Argon2id would resist GPU attacks better, but needs a third-party package.

## D-039: Registration rules: normalized email, length-only password rules, 409 on duplicates

- **Date:** 2026-10-29
- **Stage:** 03
- **Status:** Accepted

**Context:** The registration endpoint needs rules for what counts as the same email, what
passwords are allowed, and how to report an email that's already registered.

**Decision:**

- `POST /api/auth/register` takes `{ email, password }` and returns `201` with
  `{ userId, registeredAt }`.
- Emails are trimmed and lower-cased before storing and comparing, so they're case-insensitive.
- Passwords must be 8–128 characters, with no composition rules, following NIST SP 800-63B.
- An email that's already registered returns `409 Conflict`. This is detected from the unique
  constraint, so two simultaneous registrations can't both succeed.
- The endpoint isn't idempotent yet, which stage 03 allows.

**Consequences:** `409` tells anyone whether an email is registered (account enumeration). Hiding
that needs an email confirmation flow, which is out of scope. The `201` has no `Location`
header, because there's no endpoint to read a user yet.

## D-040: Access tokens are short-lived HS256 JWTs carrying only the user id

- **Date:** 2026-11-02
- **Stage:** 03
- **Status:** Accepted

**Context:** Login must return a JWT access token. Other services will need to check these tokens
without calling the Identity service on every request.

**Decision:**

- Create tokens with `JsonWebTokenHandler` (`Microsoft.IdentityModel.JsonWebTokens`), signed with
  HMAC-SHA256.
- Claims: `sub` (user id), `jti`, `iss` = `pingo-identity`, `aud` = `pingo`, `iat`, `nbf`, `exp`.
- Lifetime: 15 minutes.
- Settings come from the `Jwt` configuration section (`JwtOptions`) and are validated on startup.
  A signing key shorter than 32 bytes stops the app.
- The development signing key is in `appsettings.Development.json` and clearly named as
  development-only. Any other environment must supply its own key, for example through an
  environment variable.

**Consequences:** HS256 uses one shared secret, so any service that checks tokens could also create
them. That's acceptable while everything is ours. Moving to RS256/ES256 with a published public key
(JWKS) would let other services verify tokens without being able to create them. A JWT can't be
revoked before it expires, which is why the lifetime is short.

## D-041: Refresh tokens are random strings stored only as SHA-256 hashes

- **Date:** 2026-11-02
- **Stage:** 03
- **Status:** Accepted

**Context:** Login must also return a refresh token, described in the task as a long random string.
Whoever holds it can get new access tokens.

**Decision:** A refresh token is 32 bytes from `RandomNumberGenerator`, base64url-encoded (43
characters), valid for 30 days. The `refresh_tokens` table (migration 3) stores only its
SHA-256 hash (the primary key), the `user_id`, `created_at` and `expires_at`. Every login adds a new
row, so each device gets its own token.

**Consequences:** A leaked table can't be used to sign in. A plain fast hash is enough here, unlike
for passwords, because the token has 256 bits of randomness and can't be guessed. Expired rows are
never deleted yet, so a cleanup job will be needed later.

## D-042: Login returns one generic 401 and takes the same time for unknown emails

- **Date:** 2026-11-02
- **Stage:** 03
- **Status:** Superseded by D-045

**Context:** Login must return `401 Unauthorized` for wrong credentials. Saying which part was wrong,
or answering faster for unknown emails, would tell an attacker which emails are registered.

**Decision:** `POST /api/auth/login` returns the same `401` problem ("Invalid email or password.")
whether the email or the password is wrong. For an unknown email, the password is still checked
against a dummy PBKDF2 hash, so both cases take the same time (about 66 ms each when measured). The
database connection is released before the slow hash check. The login request only requires both
fields; length and format rules belong to registration.

**Consequences:** Login can't be used to find registered emails, although registration still can
(D-039). There's no rate limiting or lockout yet, so password guessing is only slowed by the hash
cost.

## D-043: Identity data access through small per-table repositories

- **Date:** 2026-11-02
- **Stage:** 03
- **Status:** Accepted

**Context:** `AuthService` held the SQL, the Dapper calls, the connection and transaction handling,
and the registration and login rules in one class. Step 5 would add more SQL to it.

**Decision:**

- Move the SQL into internal repositories, one per table or unit of work: `IUserRepository`
  (`TryCreateWithPasswordLoginAsync`), `IPasswordLoginRepository` (`FindByEmailAsync`) and
  `IRefreshTokenRepository` (`AddAsync`). Methods are added only when a flow needs them.
- Repositories exchange internal records (`User`, `PasswordLogin`, `StoredRefreshToken`), take
  already normalized or hashed values, and contain no business rules.
- Each repository method takes a pooled connection from `IdentityDatabase` and returns it before
  the method ends. Work that must be atomic (registration's two inserts) is one repository method
  with its own transaction.
- Expected outcomes are return values (`false`, `null`); exceptions are for real failures.
- No generic `IRepository<T>` and no Unit of Work.

**Consequences:** `AuthService` reads as the flow itself and no longer touches connections, so no
connection is held during password hashing. Two repository calls don't share a transaction; if a
flow needs that across repositories, a Unit of Work (one connection and transaction passed into the
methods) is the next step. Dapper maps rows through record constructors, which need exact types:
`timestamptz` arrives as a UTC `DateTime` and is converted to `DateTimeOffset`.

## D-044: Refresh rotates the refresh token and keeps the session's original expiry

- **Date:** 2026-11-02
- **Stage:** 03
- **Status:** Accepted

**Context:** Stage 03's refresh endpoint takes a refresh token and returns a new access token.
A refresh token that stays valid for 30 days, however often it's used, is a long-lived target if
it's stolen.

**Decision:**

- `POST /api/auth/refresh` takes `{ refreshToken }` in the body and returns the same shape as
  login: a new access token **and a new refresh token**. The old refresh token is deleted
  (rotation), so each refresh token works exactly once.
- `IRefreshTokenRepository.TryReplaceAsync` deletes the old row and inserts the new one in one
  transaction. The `DELETE`'s row count is the check: when the same token is sent several times at
  once, PostgreSQL lets only one request delete the row, and the others get `401`. Checked with 10
  simultaneous requests: one `200`, nine `401`.
- The new refresh token keeps the old one's `expires_at`. A session lasts 30 days from login
  (an absolute lifetime), however often it's refreshed.
- An unknown, expired or already used token returns the same `401` ("Invalid or expired refresh
  token."). Expiry is checked against `TimeProvider`.

**Consequences:** A stolen refresh token stops working as soon as either party uses it, and no
session outlives its 30 days. Two limits remain: reusing an already rotated token isn't treated as
theft (a full implementation would then revoke all of that user's tokens), and a client that loses
the response to a refresh (for example, a dropped connection) has to log in again, because its old
token is already used up.

## D-045: Login says whether the email or the password was wrong

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** Stage 04 asks login to return separate errors for an unknown email ("user not found")
and a wrong password. D-042 deliberately returned one generic `401` so login couldn't reveal which
emails are registered.

**Decision:** Follow the homework. `POST /api/auth/login` returns `401` with problem type
`urn:pingo:problem:user-not-found` for an unknown email and `urn:pingo:problem:wrong-password` for a
wrong password. Both stay `401`: the request is a failed sign-in either way. The dummy hash check
for unknown emails is removed: once the response says the email is unknown, equal timing hides
nothing.

**Consequences:** Login now reveals whether an email is registered, as registration already did
(D-039). Unknown emails are answered without the ~66 ms hash cost, so login is a cheap way to test
emails in bulk. Rate limiting would be the mitigation; it's not in scope yet.

## D-046: Errors are Problem Details with a stable type URN and a localized title

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Superseded by D-047

**Context:** Stage 04 asks for clear RFC 7807 errors built with the controller's `Problem()`
method. Localizing the messages was added as an extra.

**Decision:**

- `AuthController` returns errors with `ControllerBase.Problem(type, title, statusCode)`, so they
  get `application/problem+json` and a `traceId` from the standard `ProblemDetailsFactory`.
  Actions return `ActionResult<T>` instead of `Results<...>` unions, with `[ProducesResponseType]`
  attributes describing each status for OpenAPI.
- Each error has a fixed `type` URN (`urn:pingo:problem:email-taken`, `user-not-found`,
  `wrong-password`, `invalid-refresh-token`). Clients and tests should check `type`, never the text.
  URNs avoid inventing a web domain for problem types.
- `title` is localized with `IStringLocalizer<ErrorMessages>` and `.resx` files in the API's
  `Resources/` folder: English (default) and Russian. `UseRequestLocalization` picks the language
  from `Accept-Language` (or `?culture=`); unsupported languages get English.
- Localization lives in the API project: the business layer returns result values, not texts.

**Consequences:** Adding a language is one `.resx` file plus one entry in the supported cultures.
Model validation errors (`400`) are still English only; `AddDataAnnotationsLocalization` could
cover them later.

## D-047: Build errors with `TypedResults.Problem()`, not `ControllerBase.Problem()` (deviates from the task)

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** Stage 04 says to build errors with the controller's `Problem()` method. D-046 did that,
which meant changing the actions from `Results<...>` unions to `ActionResult<T>`: `Problem()` returns
an MVC `ObjectResult`, which isn't an `IResult` and so can't be part of a `Results<...>` union.

**Decision:** Deliberately deviate from the task and keep `TypedResults`:

- Actions return `Results<Created<RegisterResponse>, ProblemHttpResult>` and
  `Results<Ok<TokenResponse>, ProblemHttpResult>`, and errors are built with `TypedResults.Problem()`.
- `AddProblemDetails()` is registered, so `TypedResults.Problem()` writes through
  `IProblemDetailsService` and gets the same `traceId` as MVC's automatic `400` validation problems.
- Everything else from D-046 stays: RFC 7807 bodies (`application/problem+json`), a stable `type` URN
  per error (`urn:pingo:problem:email-taken`, `user-not-found`, `wrong-password`,
  `invalid-refresh-token`), and a `title` localized from `Accept-Language` through
  `IStringLocalizer<ErrorMessages>` with English and Russian `.resx` files.

**Consequences:** The signature lists each action's responses and the compiler checks them, and
OpenAPI reads the success responses (`200`, `201`) from it. `ProblemHttpResult` doesn't say which
status it carries, so `[ProducesResponseType]` attributes still document `400`, `401` and `409`.
This is the same style as stage 03 and as `MessagesController`. The task's `Problem()` requirement is
not met as written; the result on the wire is the same Problem Details format.

## D-048: Our own problem result types, created through `TypedResults` extension members

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** `AuthController` built its errors through a private `Error(status, code, key)` helper
that returned `ProblemHttpResult`. That read differently from the built-in `TypedResults.Ok(...)`
next to it, and `ProblemHttpResult` doesn't say which status it carries, so every `401` and `409`
needed a `[ProducesResponseType]` attribute for OpenAPI.

**Decision:**

- `ConflictProblem` (`409`) and `UnauthorizedProblem` (`401`) in `Pingo.Identity.Api.HttpResults`
  wrap a `ProblemHttpResult` from `TypedResults.Problem()`, so the response is unchanged:
  `application/problem+json`, the `type` URN (D-047), the localized `title` and a `traceId`.
  Each type implements `IEndpointMetadataProvider` and reports its own status, so
  `Results<Created<RegisterResponse>, ConflictProblem>` documents the `409` without an attribute.
- C# 14 static extension members add one method per error to `TypedResults`:
  `TypedResults.EmailTaken(messages)`, `UserNotFound(messages)`, `WrongPassword(messages)` and
  `InvalidRefreshToken(messages)`. Each sets the code and the localized title, so every error is
  defined in exactly one place.
- `[ProducesValidationProblem]` replaces the long `[ProducesResponseType]` for the automatic `400`.
  The return type can't describe that one, because the action never runs.

**Homework deviation (explicit):** stage 04 asks for errors built with the controller's `Problem()`
method. This design deliberately doesn't use it: errors go through `TypedResults.Problem()` inside
our own result types (D-047). It's the cleaner solution and ready to reuse in other services, but
it's over-engineered for a service of this size (four errors, three endpoints). The wire format is
the Problem Details the task asks for.

**Consequences:** The signatures list every response except the automatic `400`, and the compiler
checks them; a status, code or message can't be mismatched at a call site. The generated OpenAPI
document is the same as with the attributes. This is project-specific infrastructure that the
framework doesn't provide, and a new status needs one more small result type. Extension members
need C# 14, the default for .NET 10.

## D-049: Business results are CSharpFunctionalExtensions `Result<T, TError>` with error enums

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** Stage 04 introduces CSharpFunctionalExtensions: the business logic should return
`Result<T, TError>`, `Result<T>` or `Result` instead of a value or an exception. Until now each
operation had its own hand-written hierarchy (an abstract `LoginResult` with `Succeeded`,
`UserNotFound` and `WrongPassword` records, and so on: ten files for three operations).

**Decision:**

- `Pingo.Identity` references CSharpFunctionalExtensions 3.7.0 (MIT licence).
- `IAuthService` returns `Result<RegisteredUser, RegistrationError>`,
  `Result<AuthTokens, LoginError>` and `Result<AuthTokens, RefreshError>`.
- The errors are one enum per operation (`RegistrationError.EmailTaken`,
  `LoginError.UserNotFound`/`WrongPassword`, `RefreshError.InvalidToken`). A per-operation type keeps
  the compiler from letting login return a registration error. Enums are enough while no error
  carries data.
- The service returns the value or the enum directly; both convert to the `Result` implicitly.
- The controller checks `result.IsFailure`, maps `result.Error` to our problem results, and
  otherwise uses `result.Value`. `Match(...)` isn't used: its two branches return different
  `TypedResults` types, so every call would need all three generic arguments spelled out.

**Consequences:** The ten result files become four small ones, and success and failure are explicit
in every signature. The error `switch` still needs a `_ => throw` arm, because C# doesn't check
enum switches for completeness. `result.Value` throws when read on a failure, so the `IsFailure`
check has to come first. The library's chaining (`Bind`, `Map`, `Ensure`) isn't used: each flow has
one or two early exits, and plain `if`s read better there.

## D-050: Identity component tests on a shared Testcontainers PostgreSQL, reset with Respawn

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** Stage 04 asks for Identity component tests that start PostgreSQL automatically with
Testcontainers, remove it afterwards, and use Respawn to return the database to its initial state
after each test. The Identity service uses Dapper with hand-written SQL, so there's no in-memory
database to fall back on (unlike the Message tests, D-027).

**Decision:**

- New `Pingo.Identity.ComponentTests` project (xUnit 2, FluentAssertions 7, `Mvc.Testing`,
  Testcontainers.PostgreSql 4.16, Respawn 7.0, `FakeTimeProvider`), in the solution.
- `IdentityApiFactory : WebApplicationFactory<Program>` is an xUnit **collection** fixture: one
  `postgres:17` container and one app for all Identity test classes. The classes in one collection
  run one after another, which a shared database needs.
- The app runs in the `Testing` environment with the container's connection string and a test JWT
  signing key. It applies its own migrations at startup; the factory waits for them through
  `IdentityDatabase.OpenConnectionAsync()` (`InternalsVisibleTo` the test project), then builds the
  Respawner from the migrated schema.
- Respawn deletes all rows in the `public` schema **after each test** (`IAsyncLifetime.DisposeAsync`
  in `IdentityTestBase`), except `schema_migrations`.
- Problems are checked by status, media type, `type` URN and English title, so a wrong resource key
  shows up as a failing title. One test checks the Russian title.
- All Identity tests carry `[Trait("Category", "Docker")]`, so `--filter "Category!=Docker"` skips
  them as it skips the Message PostgreSQL tests.

- Concurrent refreshes go through `FindGateRefreshTokenRepository`, which holds every request after
  it has found the token until all of them have, so the race is forced on every run instead of left
  to timing (as `InsertGate` does for the Message service).
- Storage checks read the tables directly over a separate Npgsql connection with Dapper.

**Consequences:** 53 tests cover the six required scenarios plus validation limits, JWT contents,
storage (hashes only, microsecond times), forced concurrency, session expiry, localization, startup
validation and crash handling. They run in about four seconds after the container starts.
Deliberately breaking the reset, the expiry check, the login errors, the time rounding, the refresh
race check, the unique-constraint name and a Russian resource key each made the matching tests fail. Tests can't run in parallel against
the shared database. The `FakeTimeProvider` only moves forward, so later tests run at a later "now";
tests compare against `Factory.Time` instead of fixed dates.

## D-051: Fixes from the Identity test review: whole-second expiry, lifetime ranges, crash handling

- **Date:** 2026-11-03
- **Stage:** 04
- **Status:** Accepted

**Context:** A review of missing Identity tests found three defects. JWT times are whole seconds,
but `accessTokenExpiresAt` kept microseconds, so a token stopped working up to a second before the
response said. `AccessTokenLifetime` and `RefreshTokenLifetime` weren't validated, so `00:00:00`
started fine and broke every login. And with no exception handler, a crash returned a `500` with
an empty body, unlike every other error.

**Decision:**

- `TokenFactory` rounds the access token's expiry down to whole seconds, so `accessTokenExpiresAt`
  equals the token's `exp`.
- `JwtOptions` limits `AccessTokenLifetime` to 1 minute–1 day and `RefreshTokenLifetime` to
  1 minute–365 days (`[Range]`), checked at startup like the signing key.
- `app.UseExceptionHandler()` turns unhandled exceptions into a `500` Problem Details response with
  a `traceId` and without the exception's details, written through the same `IProblemDetailsService`.

**Consequences:** Each fix has a test that fails without it. Two review findings stay as they are:
whitespace-only passwords are rejected as "required" (the `[Required]` rule, despite D-039's
"length only"), and the email length is checked before trimming. Also left: two instances creating
the database at the same moment can fail with `23505` instead of the caught `42P04`.

## D-052: Daily Hangfire job with Redis storage deletes expired refresh tokens

- **Date:** 2026-11-03
- **Stage:** 05
- **Status:** Accepted

**Context:** Stage 05 asks for a background job in the Identity service that runs once a day and
deletes refresh tokens whose `ExpiresAt < now`, using Hangfire (`Hangfire.AspNetCore`) with Redis
storage (`Hangfire.Redis.StackExchange`), and an index on the expiry column.

**Decision:**

- Migration 4 adds `refresh_tokens_expires_at_idx` on `refresh_tokens (expires_at)`.
- `IRefreshTokenRepository.DeleteExpiredAsync(now)` runs `DELETE ... WHERE expires_at < @Now`.
  `IRefreshTokenCleanup` (public, in `Pingo.Identity`) calls it with `TimeProvider`'s time and logs
  the count. A token expiring exactly now is left for the next run, as the task's `<` says.
- The Hangfire wiring lives in the API project (`Jobs/HangfireSetup.cs`): Hangfire.AspNetCore 1.8.25
  and Hangfire.Redis.StackExchange 1.12.0, Redis keys prefixed `pingo-identity:hangfire:`, and a
  Hangfire server in the same process. The business project doesn't reference Hangfire.
- The recurring job `delete-expired-refresh-tokens` runs `IRefreshTokenCleanup.DeleteExpiredAsync`
  daily at 03:00 UTC (`Cron.Daily(3)`). It's registered with `AddOrUpdate` on every start, so the
  schedule in Redis always matches the code. Hangfire resolves the service from a new DI scope.
- Redis is a new `redis:8` service in `docker-compose.yml`; the connection string is
  `ConnectionStrings:Redis`. The Hangfire dashboard is mapped at `/hangfire` in Development only.
- The component tests start a Redis container next to PostgreSQL (Testcontainers.Redis 4.16.0).

**Consequences:** Expired tokens no longer pile up, and with several instances the job still runs
once, because Hangfire coordinates through Redis. The Identity service now needs Redis to start,
including in tests. The dashboard has no login; Hangfire only lets local requests in by default,
which is why it's left to Development.
