# Decision log

Architecture, tooling and convention decisions for Pingo, newest last.

**Rules**

- Add an entry in the same commit as the change that implements the decision.
- Never rewrite the decision of an accepted entry. To change course, add a new entry
  and set the old one's status to `Superseded by D-NNN`.
- Keep entries short: what was decided, why, and what it costs.

**Entry template**

```markdown
## D-NNN: <short title>

- **Date:** YYYY-MM-DD
- **Stage:** NN
- **Status:** Accepted | Superseded by D-NNN

**Context:** what problem or question came up.

**Decision:** what we chose.

**Consequences:** trade-offs, follow-ups, what this rules out.
```

---

## D-001: Build the project in C# on .NET 10

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The homework requires a `.sln`, EF Core, Blazor WebAssembly and MudBlazor.

**Decision:** Use C# on .NET 10 (the installed SDK, 10.0.401) for both backend and frontend.

**Consequences:** The whole stack is one language and one toolchain.

## D-002: Solution layout: one folder per microservice

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The task asks for `Services/<ServiceName>` and a `Frontend` folder next to it.

**Decision:** Each microservice keeps all its projects in its own folder under `Services/`
(for example `Services/Message/`). The UI lives under `Frontend/`. The `.sln` mirrors this with
solution folders.

**Consequences:** New services get a new folder. Shared code, if any, will need its own place later.

## D-003: Store messages in SQLite for the first stage

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Superseded by D-008

**Context:** Stage 01 only said "store data with EF Core".

**Decision:** Use the SQLite EF Core provider with a local `messages.db` file.

**Consequences:** Zero setup, but no real database server. SQLite can't sort by `DateTimeOffset`
in SQL, so messages were sorted in memory.

## D-004: Create the schema with `EnsureCreated`, not migrations (for now)

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The model is tiny and changing quickly.

**Decision:** Call `Database.EnsureCreated()` on startup instead of using EF Core migrations.

**Consequences:** `EnsureCreated` cannot change an existing schema. Any model change (for example
adding an edit time) needs either a dropped database or a switch to migrations. Revisit when the
model changes.

## D-005: Use `Guid` message ids

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** Messages need an id. Later the client will choose ids for idempotent `PUT` requests.

**Decision:** Use `Guid` ids from the start.

**Consequences:** Ids can be generated by the client without coordinating with the database.
Stage 02's "change id from `int` to `Guid`" is already satisfied.

## D-006: Frontend: typed API client, API address in config

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** The Blazor app is served from a different origin than the API.

**Decision:** Wrap API calls in a `MessageApiClient` class. Read the API base URL from
`wwwroot/appsettings.json`. The API allows the frontend origins through a CORS policy configured in
its `appsettings.json`.

**Consequences:** Pages don't build URLs themselves. Changing ports or hosts is a config change.

## D-007: Mark stages with two-digit annotated git tags

- **Date:** 2026-10-28
- **Stage:** 01
- **Status:** Accepted

**Context:** Reviewers need a stable pointer to each finished homework stage.

**Decision:** Tag each finished stage with an annotated tag `01`, `02`, ... The stage table in
`README.md` is updated in the tagged commit. Tags are never moved; fixes go into the next stage.

**Consequences:** The stage 01 tag was moved once, at the owner's request, when its two commits
were squashed before review. That was a one-off exception, not a change to the rule.

## D-008: Move message storage to PostgreSQL in Docker

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 requires PostgreSQL.

**Decision:** Use the Npgsql EF Core provider. Run PostgreSQL 17 locally with `docker-compose.yml`.
Put the dev connection string only in `appsettings.Development.json`.

**Consequences:** Local runs need Docker. Sorting now happens in SQL. Existing SQLite test data was
not migrated (big-bang switch to an empty database), which was acceptable because it was test data
only.

## D-009: Use `TypedResults` with explicit result types

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Endpoints returned `IResult`, which hides the possible responses.

**Decision:** Return `TypedResults` with typed signatures (for example `Task<Ok<List<...>>>`,
`Task<Created<...>>`).

**Consequences:** The compiler checks the result types, and OpenAPI picks up response codes
automatically. Responses produced outside the action (such as automatic 400s) need
`[ProducesResponseType]`.

## D-010: `GetAll` returns every message (scaffold only)

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The homework only asks to "show all messages".

**Decision:** Load and return every message with no paging. Mark it with a "Scaffold only"
comment in `MessageService.GetAllAsync`.

**Consequences:** Fine for a demo, unusable at scale. Replace with cursor-based paging (for example
`?before=<sentAt>&limit=50`) before real use.

## D-011: Use MVC controllers for the API layer

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 01 used minimal API endpoints. Stage 02 talks about controllers.

**Decision:** Replace `MessageEndpoints` with `MessagesController` (`[ApiController]`).

**Consequences:** Matches the homework wording and reviewer expectations. Slightly more ceremony
than minimal APIs.

## D-012: Split into an API layer and a `Pingo.Messages` business layer

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Stage 02 requires controllers that only accept requests and call a business layer,
without knowing what's inside it.

**Decision:** Add `Services/Message/Pingo.Messages` (class library). It owns the `DbContext`,
entities, EF Core/Npgsql packages and `MessageService`. Only `IMessageService`, `Models.*`,
`MessageLimits` and the `AddMessages(...)` DI extension are public. Everything else is `internal`.

**Consequences:** The compiler enforces the boundary: the API project cannot reach the database.
Tests that need internals will need `InternalsVisibleTo`.

## D-013: Separate database entities from business models

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The business layer needs something to return to the controller.

**Decision:** Keep `Entities.Message` (internal, mutable, shaped by the database) separate from
`Models.Message` (public immutable record, shaped by callers). Map between them in `MessageService`.
Where both are used, alias the entity as `MessageEntity`.

**Consequences:** Database changes don't leak into the API, and callers never get EF-tracked
objects. Costs a second, near-identical class and a one-line mapping.

## D-014: Validate requests with DataAnnotations, guard again in the service

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Validation was hand-written inside the endpoint.

**Decision:** Put `[Required]` and `[MaxLength(MessageLimits.MaxTextLength)]` on
`SendMessageRequest` and let `[ApiController]` return 400 automatically. `MessageService` also
checks its inputs and trims the text, so it doesn't rely on the caller.

**Consequences:** Controllers stay thin. The 2000-character limit lives in one constant shared by the
API contract and the database mapping.

## D-015: Get the current time from `TimeProvider`

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Send and edit times will be asserted in component tests.

**Decision:** Inject `TimeProvider` into `MessageService` (registered with `TryAddSingleton`)
instead of calling `DateTimeOffset.UtcNow`.

**Consequences:** Tests can swap in a fake clock.

## D-016: Name everything "Pingo"

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The homework calls the business layer `Pingo.Messages`, while the rest used
`Messenger.*`.

**Decision:** Rename the solution and projects to `Pingo.sln`, `Pingo.Messages.Api`,
`Pingo.Messages` and `Pingo.Frontend`, with matching namespaces and "Pingo" as the UI title.

**Consequences:** Kept unchanged on purpose: the GitHub repo name (`Messenger`), the local folder,
and the local PostgreSQL names (`messenger-postgres`, `messenger_messages`), because renaming them
would recreate the database.

## D-017: Use `init` for entity properties that never change

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Entity properties were all `get; set;`.

**Decision:** Make `Id` and `SentAt` `init`. Keep `Text` settable because idempotent `PUT` will
edit it.

**Consequences:** The compiler blocks accidental changes to identity and send time. EF Core still
materializes the entity through its backing fields.

## D-018: No route names on controller actions

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** Route names (`[HttpGet(Name = "GetMessages")]`) were carried over from the minimal API
version. Nothing used them for link generation.

**Decision:** Drop them.

**Consequences:** OpenAPI operations have no `operationId`, so generated clients would invent
method names. Add `[EndpointName(...)]` if a client is ever generated.

## D-019: Use the `.slnx` solution format and list docs in the solution

- **Date:** 2026-10-29
- **Stage:** 02
- **Status:** Accepted

**Context:** The solution was a classic `.sln` file: verbose, full of GUIDs, and hard to review in
diffs. Markdown docs weren't visible in the IDE's Solution Explorer.

**Decision:** Migrate `Pingo.sln` to `Pingo.slnx` (the XML solution format supported by .NET 9+
and Visual Studio 2022 17.13+), drop the unused x64/x86 platforms, and add the Markdown files as
solution items: `README.md` and `CLAUDE.md` under "Solution Items", the decision log under "docs".

**Consequences:** The solution file is short and readable in diffs. Older tooling that only
understands `.sln` can't open it. New Markdown docs must be added to `Pingo.slnx` by hand to show up
in the IDE.
